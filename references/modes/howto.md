# 实操版（howto）

## 你要解决的问题

用户想上手。给最短路径——但**先判断这个概念能不能实操**，再决定给什么。

## 前序

1. 先读 `../pyramid-rules.md` 的 **R1–R11**，特别是 **R11（行动性 vs 描述性思想）**
2. 按 `../source-discipline.md` 取材（**只用官方网页，不抓社交**）

## 第一步：分支判定（写成判定式关键句，不要写成两个平行选项）

先扫素材：
- 素材里有命令 / 代码片段 / `npm install` / `pip install` / 步骤说明 / 配置截图？→ **分支 A（可实操）**
- 素材全是讨论、观点、论文链接？→ **分支 B（只能延伸阅读）**
- **模糊时默认走分支 B**——给错误的实操步骤比给阅读清单伤害更大

输出时把判定写成一句话给用户，让他知道为什么看到的是这个：

> **判定**：<这个概念可实操吗？为什么> → 下面走 <A/B>

## 分支 A：可实操

```markdown
## 最短上手路径

**前置要求**：<必须的账号 / 硬件 / 软件，逐条列出>

### 步骤

1. **<≤15 字，动词开头>**
   具体命令或操作。
   [官方文档](url)

2. **…**（3–5 步上限，不要凑数）

### 常见坑

- 坑：<现象> → 对策：<动作>　[出处](url)

### 不适用情况

<什么情况下这套步骤走不通 / 该换别的方案>
```

硬规则：
- **每步标题必须以动词开头**（R11 行动性思想）
- 步骤按**时间顺序**（R6），能标出先后；打乱无损 = 顺序没定
- 每步后能补出「……以便产生____」且**空内为同一结果**（R11）
- 结果必须**可判定**：❌「提升检索能力」 ✅「把 P95 延迟压到 200ms 以内」
- **不许编命令**。官方文档里没见过的命令一个都不许写
- 步骤数 < 3 → 材料不够，降级到分支 B
- 不写「请确保您的系统满足要求」这类空话

## 分支 B：没法直接实操

```markdown
## 延伸阅读

<这个概念更偏理论 / 行业趋势，没有直接「跑一下」的路径。建议这样深挖：>

### 看（Top 5）

1. [标题](url) — 作者/来源，为什么值得看（≤20 字）
2. …

### 关注

- @某人 / 某项目 — 一句话说明为什么值得跟
```

硬规则：
- 清单项按**程度顺序**（重要性）排，最重要的放第一（R6）
- 每条「为什么值得看」必须具体，不写「讲得很好」
- 链接一个都不许编
